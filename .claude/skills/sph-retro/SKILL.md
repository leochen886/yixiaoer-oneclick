# 视频号复盘 & 文案教练（`history/` 数据库工作流）

本项目的全部视频复盘数据、口播全文、官方数据表快照与账号策略记忆统一存放在 `history/` JSON 数据库中：
- `history/index.json`：**AI 必读总账**（每条视频紧凑索引 + 分阶段汇总，读它即可看清全盘，不撑爆上下文）
- `history/playbook.json`：**账号策略记忆**（有效套路、避坑红线、白黄字/文案技巧、下期选题，含 `approved` / `proposed` / `rejected` 状态）
- `history/videos/<id>.json`：**单片全档**（白字/黄字/短标题/简介/完整口播/前3秒/完播率/均播时长/涨粉/窗口对照/评论/用户备注）
- `history/imports.json`：官方 CSV 导入批次与窗口记录

---

## 第一纪律：上下文读取顺序（省 token 且不遗漏）

1. **永远先读 `history/index.json` 和 `history/playbook.json`**。
   - 读取 `playbook.json` 时，**严格忽略 `status == "rejected"`（用户已划掉）的规则**，**优先遵守 `status == "approved"`（用户已拍板）的规则**。
   - 读取 `index.json` 时，**过滤掉 `status == "excluded"` 的测试/排除视频**。
2. **只按需打开特定 `history/videos/<id>.json`**：
   - 红榜 Top 视频、成熟期黑榜 Bottom 视频、同题材历史对标视频、或用户点名询问的视频，再读完整 `transcript`、`comments` 与 `window_metrics`。
3. **检查 CSV 新鲜度**：
   - 若用户刚从视频号后台「数据中心 → 视频数据 → 下载表格」导出了 `C:\Users\CL\Downloads\视频号动态数据明细.csv`，且其修改时间晚于 `history/imports.json` 最近一条记录，先提醒或执行导入：
     ```powershell
     python -X utf8 scripts/history_db.py import-csv "C:\Users\CL\Downloads\视频号动态数据明细.csv" --window 30d
     ```
   - 注意视频号后台有 **7 天（`7d`）/ 30 天（`30d`）/ 自定义（`custom`）** 口径区别：若导的是 `7d` 表，必须加 `--window 7d`（`history_db` 会自动保护超过 7 天的老视频全周期总播放不被 7 天增量覆盖，同时把 7 天增量记入 `window_metrics.7d`）。

## 工作流 A：当用户要求「复盘数据 / 看看最近跑得怎么样」

1. **先同步本地最新记录**（确保新发布的片子已在 `history/` 中）：
   ```powershell
   python -X utf8 scripts/history_db.py sync-runs
   ```
2. **严格分阶段对比（严禁拿 `<24h` 新片判死刑）**：
   - 将有效视频拆成 **成熟组（`1天` / `3天` / `7天+`）** 与 **观察组（`<24h`）**。
   - 核心评估指标不能只看播放量，必须联合看：**播放量 × 完播率（`completion_rate`）× 平均播放时长（`avg_watch_sec`）× 涨粉数/涨粉率（`follows` / `follow_rate`）× 互动率（`interaction_rate`）**。
   - 若某些老视频仅在 `window:7d` 等局部窗口口径下（`metrics_scope != "lifetime"`），明确标出口径差异，不要误判。
3. **四维归因拆解**：
   - **选题与情绪立场**：哪类题材/站队/情绪最容易过千播放或高涨粉？哪类跑偏？
   - **首帧白黄字 + 短标题**：白字是否交代了具体处境/数字、黄字是否提出悬念问题且不提前揭底？对比高播放 vs 低完播的包装差异。
   - **开头前 3 秒（`opening_3s`）与口播节奏/时长**：完播率高的片子开头第一句怎么切入？低完播的片子是不是开头绕弯或说教？
   - **评论区诉求与粉丝转化**：哪些点引发观众吵架/提问/关注？有播放没涨粉 vs 播放一般但高涨粉的差异在哪？
4. **结构化汇报 + 提出策略更新建议**：
   - 清晰输出：**① 这段时间做得好的**、**② 做得不够好/要停的坑**、**③ 写下一条文案必须注意的点**、**④ 下期选题建议**。
   - 若要将新结论写入 `history/playbook.json`，列出拟新增/调整的规则，**等用户确认后再写入（或执行 `retro_analyze.py --history-dir history` 更新建议项供用户在工作台勾选）**。

## 工作流 B：当用户要求「写文案 / 定选题 / 拟标题或黄字」（前置提醒机制）

**硬性规定：只要用户开始让你写口播脚本、定下期选题、改口播稿或拟短标题/白黄字，在动笔写正文之前，必须先读 `history/playbook.json` + `history/index.json` 中的同题材历史记录，并先给出下面 3 项提醒**：

1. **🔥 最近跑得最好的 1~2 个套路**：结合真实历史数据（点出参考视频标题、播放量、完播率、涨粉数），说明本次可以怎么借力。
2. **🚫 本次写文案必须避开的 2~3 条红线**：直接引用 `playbook.json` 里已采纳（`approved`）和有效建议（`proposed`）中的 `avoid` / `copywriting` / `hook` 规则（跳过 `rejected`）。
3. **🎯 开头前 3 秒与白黄字配合建议**：结合历史高完播样本，提醒本次第一句话怎么抓人、白字黄字如何分工（两行无标点、合计不超过 24 字、不提前揭底）。

先弹出这 3 项提醒后，再开始写文案或给选题方案；如果新视频与 `index.json` 里某条过往踩坑视频高度撞车，必须当场点名提醒风险。
